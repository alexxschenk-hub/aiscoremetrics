How the score works

Memory = model_GB + KV_GB(context) + 1 GB fits = memory ≤ usable memory Generate = η · ε · bandwidth / (active_GB + KV_GB/2) Prompt = η_c · TFLOPS · 1000 / (2 · active_params_B) Perf = fits · Gen^α · Prompt^(1−α) (selected model) Score = Perf / system price (best device = 100)

What does “fits” mean? The second formula is a yes/no check: “≤” means “less than or equal to”. Its result is used as a number in the performance formula: fits = 1 if weights, KV cache and about 1 GB of runtime overhead fit entirely in usable GPU memory; fits = 0 if the requirement exceeds it. Usable memory already accounts for the device’s reserve or GPU memory limit.

Example: A graphics card with 16 GB of VRAM has 15.2 GB usable after the assumed 0.8 GB reserve. If the model requires 14 GB in total, “fits” equals 1. At 18 GB, “fits” equals 0. In the first case, calculated performance is retained; in the second, performance and the value score for this model are 0. Running with offloading to system RAM may still be possible; the memory view shows this slower mode separately, and it does not contribute to the score.

How do you read the performance formula? “·” means multiplication, “/” division and “^” exponentiation. “Gen” means generation: how quickly the answer is produced. “Prompt” means how quickly the input is processed. Both speeds are in tokens per second. α (alpha) weights generation, and 1−α weights prompt processing. At α = 0.5, this is the geometric mean: with 100 tokens/s generation and 400 tokens/s prompt processing, “fits = 1” gives √(100 · 400) = 200. With “fits = 0”, it becomes 0. The weighting describes the score, not the fraction of time spent on a task.

The remaining quantities: model_GB is the weight size at the selected quantization. KV_GB(context) is the cache for the selected context. active_GB and active_params_B describe active weights and billions of active parameters per token; MoE models activate only part of the model. Bandwidth is in GB/s. η (eta) is assumed bandwidth efficiency, ε (epsilon) a model-dependent factor, and η_c assumed compute efficiency. TFLOPS means trillions of operations per second. The factor 1000 converts the units in the prompt formula.

From performance to score: Performance is first divided by the system price in euros. These value figures are then normalized against the best device with a known price: it receives 100 points; half its value receives 50 points. No value score is displayed without a price.

Performance applies to the selected LLM. α weighs generation against prompt processing: agentic coding 0.5 · chat 0.8 · otherwise 0.6. With long-context agents, prompt processing dominates, so compute counts for more there. The use case only filters the model list; “models that fit” counts the models in that list.

Assumptions

  • Model figures (parameters, active parameters, KV cache per token) from the model cards. For Qwen3.5/3.6, KV cache and sizes are approximations. Sizes for the newer models (including Qwen3.8, Mistral 3/4, Llama 4, DeepSeek V4/V4.1, GLM-5.3, Kimi K3, Nemotron 3) are the actual Q4_K_M GGUF files; where no Q4_K_M exists (GLM-5.3-Flash, DeepSeek V4 Pro, Kimi K3), the equally sized Q4_K_XL file. For MoE models all parameters count towards memory, the active ones only towards speed. Hybrid models (linear attention, Mamba, compressed attention) only grow a context-dependent KV cache in their attention layers; their fixed state memory is part of the overhead. Gemma 4: FP16 KV cache derived from official attention configurations, with bounded sliding windows and shared layers; backend buffers can require additional memory.
  • Gemma 4 includes E2B, E4B, 12B, 26B-A4B and 31B. E2B/E4B have 5.1/8 billion total parameters but 2.3/4.5 billion effective parameters; 26B-A4B has 25.2 billion total and 3.8 billion active. Speeds are estimates for text generation without MTP. Base and instruction-tuned weights share one hardware entry. Weights: published Q4_K_M GGUF file sizes; Q4_0: official Google QAT files. Other precisions and active bytes read are scaled estimates. Image/audio add-on weights, mobile-specific formats and MTP are outside this calculation. Google model card · QAT models
  • Quantization selectable from Q2_K (≈ 2.9 bits per weight) to FP16 (16 bits). Default is Q4_K_M (≈ 4.85 bits), native MXFP4 for the 120B MoE class. Size and bytes read per token scale with the bits; the KV cache stays FP16.
  • Usable memory: GPU = VRAM − 0.8 GB. Mac: macOS default limit of 67% (≤ 36 GB) or 75% of RAM, but at most RAM minus 6 GB for macOS and background apps. With the raised limit, everything except those 6 GB. Ryzen AI Max: 96 GB, 110 GB raised, 4 GB Linux reserve.
  • Bandwidth efficiency η: NVIDIA 0.60, AMD graphics cards 0.50 (ROCm/Vulkan), Ryzen AI Max 0.72, Apple Pro/Max 0.62, Apple Ultra 0.50.
  • Ryzen AI Max+ 395: of 128 GB, about 96 GB is usable as graphics memory on Linux, about 110 GB with a raised limit.
  • NVIDIA GB10 (DGX Spark, Surface RTX Spark Dev Box): 273 GB/s LPDDR5X, shared memory. Usable by the GPU: DGX Spark 128 GB ≈ 119 GB (124 GB raised), DGX Spark 64 GB ≈ 56 GB (8 GB reserved for the system per NVIDIA), Surface 112 GB per Microsoft. Bandwidth efficiency η 0.72 as for Ryzen AI Max; compute 1,000 AI TOPS ÷ 8 = 125 TFLOPS, η_c 0.3. Microsoft has not published the Surface bandwidth; it is assumed to match the DGX Spark.
  • Compute: NVIDIA = FP16 tensor throughput (Blackwell: AI TOPS ÷ 8, Ada: ÷ 4), η_c 0.5. AMD = datasheet FP16 peak, η_c 0.35 (Ryzen AI Max 0.3). Apple = GPU FP32, η_c 0.6. M5 chips with Neural Accelerators ×3.5 (Apple claims up to 3.9–4× over the previous generation).
  • MoE models reach about half their theoretical generation speed in practice (routing, attention, scattered reads), so ε = 0.55. Dense models ε = 1.
  • Power use: graphics cards use the manufacturer's board power plus 150 W for the rest of the PC (laptops plus 60 W), i.e. a full-load estimate. Macs use about 50% of Apple's maximum wall power (measured: M3 Ultra 138 W at a 270 W maximum), MacBook Pros the power adapter as the upper bound. Mini PCs use measured or vendor figures: Ryzen AI Max+ 395 about 128 W, DGX Spark 140 W, Surface RTX Spark Dev Box 100 W. Electricity cost = watts × hours × 365 × price ÷ 1,000; total cost over 3 years = system price + 3 × electricity at 8 h/day.
  • No partial offloading: a model that does not fit scores 0. Multi-GPU is not modelled.

Real-world numbers

  • First token = prompt length ÷ prompt processing speed. Very long prompts are somewhat slower in practice because attention grows too.
  • Memory usage: weights + KV cache for the context + about 1 GB runtime overhead. If that does not fit in graphics memory, the rest of the weights moves to PC RAM (DDR5 dual channel, about 58 GB/s effective). Every token then has to read that part through the much slower system memory. 8 GB of PC RAM are reserved for the OS and apps.
  • 100 lines of code ≈ 1,100 tokens (about 11 tokens per line). Time = first token + 1,100 ÷ tokens/s.
  • Images are compute-bound. Reference RTX 4090 at 1024 × 1024: SDXL 30 steps ≈ 4.5 s, FLUX.1 schnell ≈ 2.2 s, FLUX.1 dev ≈ 14 s. Other devices are scaled by compute, with a platform factor for Apple (2.1) and AMD (1.7), calibrated against typical SDXL times.
